# Инструменты MCP-сервера — gtfs-assistant

Сервер: `src/server.py`. Вся логика расчётов — в `src/gtfs_queries.py`,
обычный Python/SQL, без участия модели (модель только выбирает
инструмент, параметры и формулирует ответ словами — как того требует ТЗ).

Проверить любой инструмент можно без модели и без Telegram — через
MCP Inspector:
```
npx @modelcontextprotocol/inspector python src/server.py
```

---

## 1. `find_stop`

Найти остановку по неточному названию или по координатам (геопозиция).

**Параметры** (все опциональны, но нужен хотя бы один способ поиска):
| Имя | Тип | Описание |
|---|---|---|
| `query` | string | Часть названия остановки, нечувствительно к регистру |
| `lat` | float | Широта (для поиска по геопозиции) |
| `lon` | float | Долгота (для поиска по геопозиции) |

**Возвращает:** список остановок — `stop_id`, `stop_name`, `stop_lat`,
`stop_lon`, и (при поиске по координатам) `distance_m` — расстояние в
метрах, отсортировано по близости.

**Почему границы такие:** сервер **не решает сам**, какую остановку
выбрать при нескольких совпадениях — просто возвращает все найденные
(до 5 штук). Решение "уточнить у пользователя, а не выбрать молча" —
осознанно оставлено агенту/боту, а не зашито в сервер: сервер не знает
контекста диалога, а агент — знает.

## 2. `get_next_departures`

Ближайшие отправления с остановки, на "сейчас" или на конкретную
дату/время, с учётом календаря работы маршрутов.

**Параметры:**
| Имя | Тип | Обязателен | Описание |
|---|---|---|---|
| `stop_id` | string | да | ID остановки, из результата `find_stop` |
| `route_short_name` | string | нет | Фильтр по номеру маршрута, например "12" |
| `date` | string | нет | Формат `YYYY-MM-DD`. Без даты — сегодня |
| `time` | string | нет | Формат `HH:MM`. Без времени — сейчас |

**Возвращает:** список ближайших отправлений (до 5) — `route_short_name`,
`trip_headsign` (направление), `departure_time`.

**Почему границы такие:** `route_short_name` — опциональный фильтр, а не
отдельный обязательный параметр, потому что вопрос "когда следующий
автобус вообще" (без указания маршрута) — тоже валидный сценарий из ТЗ.
Учитывается и `calendar.txt`, и `calendar_dates.txt` (исключения из
календаря — праздники, отменённые рейсы), и рейсы после полуночи
(`departure_time` вида `25:10:00`), чтобы не пропустить последние рейсы
дня. Дата и время — раздельные необязательные параметры, а не единый
datetime-объект, потому что языковой модели проще и надёжнее передавать
их по отдельности, разбирая человеческую фразу вроде "а в воскресенье в
6 утра".

## 3. `get_routes_through_stop`

Какие маршруты проходят через остановку — направления и часы работы.

**Параметры:**
| Имя | Тип | Обязателен | Описание |
|---|---|---|---|
| `stop_id` | string | да | ID остановки, из результата `find_stop` |

**Возвращает:** список — `route_short_name`, `trip_headsign`,
`first_departure`, `last_departure` (часы работы этого направления за
весь период данных). Один маршрут может встретиться несколько раз — по
разу на каждое уникальное направление.

**Почему границы такие:** этот инструмент **намеренно не фильтрует по
дню недели** — он отвечает на вопрос "что здесь вообще ходит", а не "что
ходит сегодня". Для последнего есть отдельный инструмент
(`get_next_departures`) — разделение сделано, чтобы не путать два разных
по смыслу вопроса пассажира в одном инструменте с кучей опциональных
флагов.

## 4. `get_fare`

Цена проезда для маршрута, если она есть в данных.

**Параметры:**
| Имя | Тип | Обязателен | Описание |
|---|---|---|---|
| `route_short_name` | string | да | Номер маршрута |

**Возвращает:**
- `{"available": true, "price": "...", "currency": "..."}` — если цена
  найдена в `fare_attributes.txt`/`fare_rules.txt`
- `{"available": false}` — если данных нет

**Почему границы такие:** возвращается явный флаг `available`, а не
пустой список или `null` — чтобы агент не мог перепутать "цены нет в
данных" с "инструмент не сработал". Это прямая реализация требования
ТЗ: "не знаю" должно быть явным честным ответом, а не побочным эффектом
пустого результата. Для вопросов о живой позиции транспорта
("автобус сейчас где?") инструмента нет вообще — в GTFS Schedule таких
данных не бывает никогда, и это явно написано в docstring инструмента,
чтобы агент не пытался угадать, чем это можно вызвать.

## 5. `plan_trip`

Маршрут от одной остановки до другой: сначала прямой, если нет — с
одной пересадкой.

**Параметры:**
| Имя | Тип | Обязателен | Описание |
|---|---|---|---|
| `from_stop_id` | string | да | ID начальной остановки |
| `to_stop_id` | string | да | ID конечной остановки |
| `date` | string | нет | Формат `YYYY-MM-DD` |
| `time` | string | нет | Формат `HH:MM`, желаемое время отправления |

**Возвращает:** список вариантов поездки (до 5), каждый — либо прямой
рейс (`route_short_name`, `departure_time`, `arrival_time`), либо
поездка с пересадкой (`transfer_stop_id`, `transfer_stop_name`,
`first_leg`, `second_leg` — с временами и маршрутами обоих отрезков).

**Почему границы такие:** сначала ищется прямой маршрут, и только если
его нет — вариант с пересадкой (не наоборот и не одновременно), чтобы не
предлагать пассажиру пересадку там, где можно доехать без неё. Пересадка
ограничена одной (как того требует ТЗ) — учитывается минимальное время
на пересадку (3 минуты) между прибытием одного рейса и отправлением
следующего с той же остановки.

**Известное ограничение:** в отличие от `get_next_departures`, не
проверяет рейсы после полуночи предыдущего дня — для дневных вопросов
не критично, но для очень ранних/поздних поездок с пересадкой возможны
неполные результаты (см. REPORT.md, раздел "Известные ограничения").

## Общий принцип границ между инструментами

Пять инструментов соответствуют пяти обязательным типам вопросов из
ТЗ один-к-одному — осознанное решение, а не совпадение: каждый вопрос
пассажира из раздела 2 ТЗ требует отдельного вида расчёта (поиск,
время, направления, деньги, маршрут), и смешивание их в один инструмент
с множеством опциональных флагов сделало бы описание для модели
(и для человека) более запутанным, а не проще.
