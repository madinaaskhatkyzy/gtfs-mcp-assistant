# GOAL — gtfs-mcp-assistant

Дата создания: 2026-09-23 (день 1)
Статус: зафиксировано. Изменения не вносятся сюда — только в TRACE.md.

## Цель

Собрать Telegram-ассистента, который отвечает на вопросы пассажира о
расписании городского транспорта (GTFS), беря каждый факт через
инструменты MCP, и доказать измерением на ≥50 вопросах, что он отвечает
верно.

## Из чего состоит результат (4 части)

1. **MCP-сервер** — инструменты для запросов к GTFS (остановки, ближайшие
   рейсы, маршруты через остановку, маршрут A→B, "не знаю" для того,
   чего нет в данных). Работает автономно, без Telegram и без агента —
   проверяется через MCP Inspector.
2. **Агент на LLM** — превращает вопрос пассажира в вызовы инструментов
   MCP-сервера и формулирует ответ словами. Модель НЕ считает расписание
   сама.
3. **Telegram-бот** — интерфейс: принимает текст и геопозицию,
   удерживает контекст на один шаг диалога.
4. **Проверочный контур** — набор ≥50 вопросов с заранее известным
   правильным ответом (получен не через бота) и метрика: доля верных /
   неверных / "не знаю" ответов, с разбором ошибок.

## Порядок (почему так)

1. Выбор города (Mobility Database, ≥50 маршрутов) + прогон через GTFS
   Validator — без этого шага всё остальное можно строить на плохих
   данных и не узнать об этом до конца недели.
2. MCP-сервер с инструментами доступа к GTFS — это ядро; агент и бот —
   тонкие обёртки поверх него.
3. Проверка сервера через MCP Inspector (без модели) — быстрая обратная
   связь, не тратим вызовы модели на отладку самого сервера.
4. Агент на LLM поверх сервера.
5. Telegram-бот поверх агента.
6. Проверочный набор вопросов — собирается **параллельно с шагом 1-2**,
   не в конце (иначе есть риск подгонки под то, что бот уже умеет).
7. Прогон проверочного контура, разбор ошибок, отчёт.

## Самое рискованное — и почему

**Риск №1: качество и полнота GTFS-фида выбранного города.**
Публичные фиды бывают с ошибками (устаревший calendar, отсутствующие
stop_times для части рейсов, кривые частоты). Если это всплывёт на
шаге 5-6, придётся менять город и переделывать проверочный набор.
Смягчение: валидатор — до начала работы, не после.

**Риск №2: маршрут A→B с пересадкой (вопрос типа 4)** — самый сложный
инструмент сервера с точки зрения алгоритма (нужен поиск по времени
с учётом календаря и часового пояса). Может занять непропорционально
много времени относительно остальных 4 типов вопросов.
Смягчение: делать последним из инструментов сервера, когда остальные
типы уже работают и измеряются.

## Критерий "работает"

Бот честно отвечает "не знаю" там, где в данных факта нет (вопрос 5),
и не выдумывает время/маршрут там, где данные есть, но что-то не найдено
(например: остановка не найдена → уточняющий вопрос, а не случайный
выбор). Метрика проверочного контура посчитана и в отчёте объяснено,
чего она не видит.
